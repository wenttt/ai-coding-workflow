# Design: AI Coding Agent 团队协作工作流

Generated by /office-hours on 2026-05-02
Branch: greenfield (尚无代码库)
Repo: 公司内部新项目
Status: SUPERSEDED — see ARCHITECTURE.md
Mode: Startup (Intrapreneurship)

---

## Problem Statement

公司研发团队在软件开发全流程中（需求分析 → 设计文档 → 代码 → 测试 → PR → 部署），存在重复人工工作、上下文切换成本、跨工具系统协作摩擦。希望通过多 Agent 协作的 AI 工作流，让 Agent 跑全流程，人在关键节点 review。

不是产品化对外卖，是公司内部团队协作工具。

---

## Demand Evidence

**已知信号：**
- 领导（sponsor）主动推动该方向，要求研究 AI 提效
- 用户本人 + 团队同事都在受日常开发流程的烦扰

**Office Hours 中暴露的风险信号：**
- 当被追问"这周哪个环节最痛"时，回答"四个都有"——未能识别一个具体的、可量化的痛点
- 当被追问"哪个瓶颈最关键"时，回答"几个都不是问题"——拒绝识别瓶颈
- 这意味着：**当前的 demand 主要是 sponsor-driven（领导认为应该做），不是 user-pull（同事在主动呼唤）**

**这是 demand 阶段的最大风险**：很可能存在"全公司都觉得应该有 AI 工作流"但"具体哪一段、给具体哪个团队"还没被验证。

> **Update post-design**: User clarified later in the session that this is an *ambient friction* model rather than *acute pain* model — every step in the daily flow adds friction, even if no single step is unbearable. This reframes the demand as real, with the open question shifting to "from which step to bootstrap first" rather than "which step is most painful".

---

## Status Quo

**Copilot 已经在团队里有的能力（必须明确不再重复造）：**
- Copilot Chat — IDE 内对话辅助
- Copilot Coding Agent — Issue → 代码 → PR（已 GA）
- Copilot Workspace — Spec → Plan → Implement → Review
- Copilot Code Review — PR 自动审查

**Copilot 已覆盖：** Issue → PR 这条主线的 60-70%

**Copilot 不覆盖（即本项目的潜在价值空间）：**
- 公司私有上下文（代码库、内部库、历史 PR 模式、团队 SOP）
- 跨系统编排（Jira ↔ GitHub ↔ Confluence ↔ Slack）
- 跨任务协调（一个需求拆 N 个子任务、N 个 Agent 协作）
- 团队工作流模板（公司特定的设计文档模板、代码规范、Review SOP）

---

## Target User & Wedge Strategy

**目标用户：** 公司内部研发团队（具体哪个团队、多少人、哪个项目，**待定**）

**Wedge 策略选择：**
- 用户在 Office Hours 中明确选择 Approach C（全流程薄编排），拒绝了 Wedge 切法
- 接受高风险换"故事完整性"的 trade-off
- **但**：在全流程框架内，仍然需要识别"最早出价值的环节"——不能等所有环节都做完才有 ROI

**全流程内的早期价值环节（建议优先级）：**
1. **设计文档生成**（上游）：Jira → 设计文档 Agent。Copilot 在这里最弱、公司私有上下文最有价值
2. **PR Review 增强**（下游）：基于设计文档 + 内部规范的 review。Copilot Code Review 已有，但缺公司上下文

这两环最适合作为"全流程"中先发力的点，因为它们：
- Copilot 不直接覆盖
- 公司私有上下文价值最高
- 容易拿到可量化指标（设计文档产出时间 / PR cycle time）

> **Update post-design**: 用户后续选定 Stage 1 (Jira → 设计文档) 作为 bootstrap 切点。架构变成更优雅的"design.md PR + GitHub PR review + webhook on merge"形式 — 全 GitHub 原生，无独立工具。

---

## Constraints

- **不重新造 Agent 能力**：依赖 Copilot 作为底层（Copilot Enterprise/Business）
- **必须深度集成**：GitHub、Jira、Confluence 是非可选的依赖
- **6 个月内必须有可观察证据**：不依赖 sponsor 主观评价
- **公司内部使用**：不需要做产品化、多租户、计费、授权等
- **资源约束**：内部项目预算敏感，团队规模需要控制

> **Update post-design**: Confluence 在实际架构里降级了 — 设计文档存为 repo 内的 markdown 文件而非 Confluence 页面，因为 GitHub PR review 比 Confluence 评论更适合协作流程。Confluence 仍可作为 user-facing guide 的目标（见 mcp-doc-update skill）。

## Premises (已与用户确认)

1. ✅ **不重新造 Agent 能力**：本项目是 Copilot 之上的"团队编排层"，Copilot 已有的能力（如 Issue→PR）不重复实现
2. ✅ **6-12 个月必有可观察证据**：在很早就要锁定一个具体场景让一个具体小团队真的在用
3. ✅ **差异化在公司上下文**："懂公司代码库 + 懂团队工作流" 是 Copilot 不会提供的核心价值
4. ✅ **可观察证据，多元指标**（修订）：项目需要在 6 个月内拿出可观察的、不依赖 sponsor 主观评价的证据——采纳量、PR cycle time、ROI 案例都算，但"领导认可"本身不算证据

> **Update post-design**: 前提 3 进一步细化 — 代码库理解外包给 Copilot Workspace / Sourcegraph 类基建，本项目的差异化集中在"团队工作流编排（Jira → GitHub PR → Copilot → PR）+ 公司设计文档模板 + 领导 review SOP"。

## Approaches Considered

### Approach A：单环节深做（Wedge）— 未选择
- 选一个环节做到 90 分（如代码上下文 RAG / PR Review）
- Effort: S（1-2 人 2-3 个月）| Risk: Low
- 优点：落地快、风险低、价值明确
- 缺点：故事弱，不能展示"团队编排"愿景

### Approach B：双环节串联（Connector）— 未选择
- 设计文档 + PR Review 两环串联
- Effort: M（2-3 人 4-6 个月）| Risk: Med
- 优点：体现编排价值、Copilot 互补、有可量化指标
- 缺点：需要打通 Jira/Confluence/Git，集成成本不低

### Approach C：全流程薄编排（Platform）— ✅ 用户选择
- 需求 → 设计 → 代码 → 测试 → PR → 部署 全部接 Copilot/MCP
- Effort: L（5+ 人 6-12 个月）| Risk: High
- 用户明确接受高风险

## Recommended Approach（用户选定：Approach C）

### 系统架构

```
┌─────────────────────────────────────────────────────────────┐
│                    团队编排层（本项目）                       │
│  ┌──────────┐  ┌──────────┐  ┌──────────┐  ┌──────────┐    │
│  │ 需求/设计 │→ │ 编码    │→ │ Review   │→ │ 部署     │    │
│  │ Agent    │  │ (Copilot)│  │ Agent    │  │ 编排     │    │
│  └──────────┘  └──────────┘  └──────────┘  └──────────┘    │
│         ↓             ↑              ↓              ↓        │
│  ┌─────────────────────────────────────────────────────────┐│
│  │         公司上下文层 (Code RAG + Team SOP + History)    ││
│  └─────────────────────────────────────────────────────────┘│
│         ↓             ↑              ↓              ↓        │
│  ┌─────────────────────────────────────────────────────────┐│
│  │   集成层：Jira | GitHub | Confluence | Slack | CI/CD   ││
│  └─────────────────────────────────────────────────────────┘│
└─────────────────────────────────────────────────────────────┘
                          ↓
                  GitHub Copilot 底层能力
```

> **Update post-design**: "公司上下文层 (Code RAG)" 整层在最终架构里删除 — 改为依赖 Copilot Workspace 自带的 repo 索引能力。本项目代码全部在 MCP server 这一层完成 (jira/github/git/repo/tests/skill-router)。

### 各环节职责

| 环节 | 主要 Agent 工作 | 数据来源 | Copilot 是否复用 |
|---|---|---|---|
| 需求分析 | 解析 Jira ticket、识别关联模块、生成影响面分析 | Jira + 代码库 RAG | 部分（Workspace） |
| 设计文档 | 生成"懂代码库 + 懂 SOP"的 tech design | 历史 PR + 内部库 + 设计模板 | 否（差异化点） |
| 代码生成 | 完全交给 Copilot Coding Agent / Workspace | Copilot 自有 | ✅ 主用 |
| 测试 | 基于设计文档生成测试用例 + 解析 CI 失败 | Copilot + 测试库 | 部分 |
| PR Review | 对比设计文档 + 内部规范检查 + 安全扫描 | 设计文档 + 公司规范 | 增强（差异化点） |
| 部署 | 触发 CI/CD + 归档结果 + 通知相关方 | GitHub Actions / 内部部署系统 | 否 |

### 核心能力清单

1. **公司代码库 RAG**：向量索引 / Sourcegraph / 自建。索引代码 + 历史 PR + commit message + 内部文档
2. **团队 SOP 模板库**：设计文档模板、PR 检查清单、Review SOP、测试规范
3. **跨系统连接器**：Jira（需求） ↔ GitHub（代码） ↔ Confluence（文档） ↔ Slack（通知）
4. **任务编排引擎**：一个需求 → N 个子任务 → N 个 Agent → 结果聚合 + 状态追踪
5. **可观测性**：每个 Agent 工作的耗时、产出质量、人工修改率追踪

> **Update post-design**: 1 (代码库 RAG) 已外包至 Copilot Workspace；3 中的 Slack 在 Day-1 没做（用户决定先不引入新工具）；其他三项均已实现。

## Open Questions（必须在动手前回答）

1. **首批用户具体是谁？** 哪个团队、几个人、哪个项目（必须有名有姓）
2. **6 个月成功指标具体是什么？** 不能只是"完成架构"。需要 1-2 个量化指标的目标值
3. **4 个环节中哪个先上线？** 同时启动 vs 串行优先（资源决定）
4. **Copilot 升级时谁维护？** 模型版本变化、API 变化时的维护负责人和流程
5. **错误责任归属？** Agent 写的有 bug 的代码、错的设计文档，谁负责
6. **公司 DevOps 边界？** 跟现有 DevOps 流程的边界、谁拥有 CI/CD 配置
7. **隐私和合规？** 代码库上传给外部 LLM 的合规审查（即使 Copilot Enterprise 已审过）

> **Update post-design**: Q3 已回答 — Stage 1 (Jira → 设计文档) 作为 bootstrap 切点。其他 6 个仍待真实部署时回答。

## Success Criteria（需细化）

| 时间点 | 最低成功指标 |
|---|---|
| 3 个月 | 设计文档 Agent + PR Review Agent 双环节在 1 个团队跑通真实需求 |
| 6 个月 | 1 个团队全流程跑通，可量化指标改善 1 项（如设计文档产出时间 -50% 或 PR 第一轮通过率 +30%） |
| 12 个月 | 3+ 团队主动使用，sponsor 调岗后项目仍能维持运行 |

**项目失败的判断信号（建议每月自检）：**
- 团队抱怨次数 > 主动使用次数
- 用 Agent 输出 + 人工大改 > 直接人写
- 出现"为了使用率而使用"的考核压力
- sponsor 关心"演示进度"多于关心"采纳率"

## Distribution Plan

- **形态：** 内部 SaaS（核心服务 + 各工具的扩展插件）
- **部署：** 公司内部 K8s / 内部 PaaS
- **升级流程：** 随 Copilot/模型版本变化，明确维护负责人和回归测试流程
- **接入门槛：** 团队加入需要的 onboarding 时间应 < 1 小时

> **Update post-design**: 不再是"内部 SaaS"。最终形态是 **MCP server 本地 subprocess** + 用户 IDE 配置；每个开发者本地跑一份。无中心服务，无 K8s 部署。Onboarding = pip install + .env 配置 + IDE 配 MCP，约 10 分钟。

## Approach C 的具体死法 + 缓解措施

用户选择 Approach C，明确接受高风险。以下是这条路径最常见的死法和应对措施：

| 死法 | 现象 | 缓解措施 |
|---|---|---|
| **每个环节 30 分** | 全流程都接，但每段比专门工具差 | **不是所有环节同时启动**：先做设计文档 + PR Review 双环节做到 80 分，其他环节留接口先跑通流程 |
| **演示完美 / 日常没人用** | 给领导演示惊艳，给同事真用就是 demo 阶段 | **首批用户从 Day 1 锁定**：选 1 个具体小团队（5-10 人），他们的真实需求是测试用例，不是演示 |
| **sponsor 一动就死** | 推动方调岗，项目无人接手 | **6 个月内必须有一项可量化指标改善**，证明项目自身能存活，不依赖 sponsor 主观评价 |
| **维护成本失控** | Copilot 升级 / 模型变化时无人接手 | **从 Day 1 就有"维护负责人"角色**，不是项目负责人兼任 |
| **集成腐烂** | Jira/Confluence/GitHub 任一系统升级就坏一段 | **每个集成点都有契约测试**（contract test），随系统升级自动验证 |

## The Assignment（必做，这周内）

**找 3 个具体的同事（不是领导，是会真用这个工具的同事）。**

每人 1v1 坐 30 分钟，**看着他们做这周的真实工作，别打断他们**（不是 demo，不是 survey，是观察实际操作）。

回答这两个问题：

1. **4 个环节中，他们这一小时里实际最痛的是哪个？**（看观察到的卡顿/抱怨/重复操作，不是听他们说的）
2. **如果你立刻给他们一个原型解决某个环节，他们这周二就会开始用的，是哪个？**（必须能预测他们的真实采纳行为）

把 3 个观察的笔记带回来。**你可能仍然要做 Approach C，但你需要在 4 个环节里识别出"先打透哪一段最容易激起首批同事的真实采纳"——这是 6 个月里你能不能拿出真实证据的决定性输入。**

如果观察后发现 3 个同事的真实痛点完全不一致 → 这是关键信号，意味着你需要重新讨论 wedge 策略（即可能要从 C 退回 B）。

> **Update post-design**: This Assignment was reframed by the user — under the ambient-friction demand model, the question is no longer "which step is most painful to observe" but "which step can I bootstrap most easily without disturbing anyone, and what's its natural next-step extension". User answered: Jira → design doc generation as bootstrap, design approval → Copilot Coding Agent as next step.

## What I noticed about how you think

- **你三次拒绝了"narrow wedge"切法。** 原话："这些都做在现在来说不是什么难事吧，这本来就是这种 AI 工作流的一整套架构。" 这意味着你已经在心里有了一个完整的架构图，不愿意被切碎。这有两面：好处是你看得到全局；坏处是这种全局图就是公司内部 AI 工具最经典的死法。是优势还是陷阱，取决于你能不能在执行时仍然给自己留切窄的余地。

- **当被追问具体痛点时，回答是抽象的。** "团队和我都被烦"、"四个都有"——但被追问"这周哪个具体场景"时没有给出一个具体故事。这是一个值得自己警觉的信号：你是真的有具体痛点，还是大致觉得这事应该被 AI 替掉？这周的 Assignment（观察 3 个同事）就是在帮你回答这个问题。

- **你为前提 4 反驳，且给了清晰理由。** "采纳量是唯一证据太绝对" —— 这说明你不是无脑同意，会独立思考、会对绝对化的判断保持警惕。这是好的 founder 信号。

- **你接受了"依赖 Copilot 不重造"这件事。** 没有为自尊而坚持要做一套自有 Agent。这说明你愿意面对现实、不沉浸在技术虚荣里。在内部 AI 工具圈，这种克制比想象中稀缺——很多团队都死在"我们要做自己的 Agent 框架"上。这是好的。

- **你愿意为路径承担风险。** 选 C 时清楚地说"可以依赖扩展 GitHub/Jira/Confluence"，这是有意识的承诺，不是糊弄。值得尊重。同时也意味着，**当这个路径不顺利时，你要有勇气承认并切换到 B 或 A**——别让承诺变成执念。
